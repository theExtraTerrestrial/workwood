Round 22: seeing the commands, and how long they take

Opening the steps under a reply today shows a box of identical lines, each a green tick and the word Running followed by the agent's own description. You can't see what actually ran, whether it is still running, or how long it took. Claude Code's terminal shows all three. This round brings that into the conversation, without making the thread noisy for people who never open the steps.

  • “Running” repeats on every command and says nothing; the tick is always green, even for a command that failed.
  • The command is never shown. “Show working tree status” could be anything; you have to trust the description.
  • No time. A 2-second command and a 4-minute build look the same, and a step that is still going looks done.

A step list with the command in a code block

AEach step gets a header and, for commands, its own code blockRecommended

The open list becomes a thin rail of steps. The header is the verb in bold, the agent's description, and the time it took on the right. A command's actual text sits underneath in a code block: monospace, wrapped, escaped exactly as sent, with a copy button. Reads, edits and searches stay one line each, because their header already says everything. Long commands clip at four lines with a fade.

  • Past tense once it's finished: “Ran”, “Read”, “Edited”. “Running” only while it is.
  • Time on every step, right-aligned so the slow ones stand out; the summary line carries the total time spent in tools.
  • A failed command is red: red dot, exit 1 tag, and the last three lines of its output under the command. Output stays hidden for commands that succeed.
  • Escaped, never rendered. The command goes in as text, so heredocs, <, backticks and $(…) show exactly as sent. Light colouring only for the program name and quoted strings.
  • The description is still there, in the header. The code is what you read when you want to check it.

BOne line per step, showing the command; the block opens on click

Denser: each row is the command itself in monospace, the description faded beside it, and the time. Clicking a row opens the full command and its output beneath. Better for turns with twenty commands; worse for reading what a long command does, because the first line of a heredoc is rarely the interesting part.

While it runs

Claude Code keeps a clock on the step that's in progress. Here the bottom of the thread does the same: the working line names what is running and counts up, and the command is shown right there, so you can see a stuck npm install or a wrong path before it finishes and stop it.   • The clock counts up from the moment the command starts, not from the start of the turn. The turn's own time stays in the summary line and the “Worked for” footer.
  • Stop stops this one command, not the whole run (same as Esc on a stuck tool in Claude Code). Only shown on a running command.
  • When the agent set a time limit, it shows as “stops itself after 10m” — that's Claude Code's (timeout 10m).
  • A command sent to the background gets an in background tag and keeps its clock running until it exits, even after later steps finish.

How time is written

Short and relative, the way Claude Code does it: one decimal under ten seconds, whole seconds to a minute, then minutes and seconds, then hours and minutes. Tabular figures so the column doesn't jitter while it counts.

80 ms2.4 s48 s73 s246 s3 900 s 0.1s2.4s48s1m 13s4m 06s1h 5m

What the service needs to send

  • Each step today is {verb, what, group} from describe() in service/transcript.mjs. Add id, cmd (the full command for Bash, the pattern and path for Grep/Glob), start and end (timestamps of the tool_use and its matching tool_result), error (from is_error, with the exit code parsed from the result when there is one), bg and timeout.
  • A short output tail (last ~3 lines, capped in size) only for failed commands; the full output loads on “Show all output”, so transcripts stay small.
  • The running step's clock is drawn in the app from start, the same way the existing elapsed counter is; the service doesn't push ticks.
  • The command is put in the page with text, never through the markdown renderer, so nothing in it can be read as formatting.

Open questions

  • Should commands that succeed also offer “Show output”, collapsed, or is the red tail on failures enough?
  • Should the steps of the turn in progress be open by default, closing themselves when the reply arrives? That is closest to watching Claude Code's terminal.
  • A or B, or A with a switch to B once a turn passes ~12 commands?
