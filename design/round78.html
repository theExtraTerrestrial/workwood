Under the hood
  • Finding them. Every few seconds, while a session is open, the service lists the ports being listened on and their processes (/proc on Linux and WSL, lsof on macOS). It reads each process's folder and command line and matches the most specific worktree, so .claude/worktrees/x is never listed under main as well. Parents and children are grouped.
  • What counts as a server. A process counts if it listens on a port, belongs to the same group as one that does, or matches a line in the repo's Procfile. That is how Sidekiq is found. Editors, language servers, the agent's claude and idle shells stay out.
  • The agent's own servers. A listening process that descends from the session's claude process adds its port to the agent's existing task row. It does not get a row of its own. It still ends with the session, because Claude Code stops its shells.
  • Who started it. The row says Workwood, agent or yours. Logs and Restart need the output or the command, so a process started outside Workwood gets Open and Stop only. Restart also works when its command matches a Procfile line.
  • Stop. SIGTERM to the process group, then SIGKILL after 5 s. Before stopping a process Workwood didn't start, it asks.
  • The repo's list. If .workwood/servers.json is missing, Workwood falls back to Procfile.dev, then Procfile: 
    {
  "procfile": "Procfile.dev",
  "setup": "bin/worktree-setup",       // once per worktree, before the first start
  "teardown": "bin/worktree-teardown", // when the worktree is removed
  "open": "web"
}
    Each process gets PORT (different in each worktree), WORKWOOD_WORKTREE and WORKWOOD_BRANCH. The repo's scripts copy the database and pick the Redis namespace. Workwood knows nothing about Foreman or Rails.
  • Servers started by Workwood run in the service like terminals (node-pty). They keep running after the session goes idle and stop when the worktree is removed. The agent can start them too, with workwood serve web.

Open questions

  1. Should the quiet Start servers line (3) always show when nothing runs? Or only through the ⋮ menu and /serve?
  2. When the repo lists servers, should Workwood tell the agent to start them with workwood serve, so they outlive the session and you see the logs? Or leave the agent to start them its own way?
  3. When Workwood quits, should the servers it started stop with it, or be listed in the quit dialog next to background tasks?
  4. Should a session's row in the sidebar show a small green port badge while it has a server running?
